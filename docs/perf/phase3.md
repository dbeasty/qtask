# Phase 3 (LAN sync) performance

Generated by `npx tsx scripts/perf-phase3.ts` on 2026-10-11 (run took 19 s).

## Environment

- Apple M3 Max, 16 logical cores, 48 GiB RAM, darwin 25.5.0, Node v26.0.0
- All "devices" are separate Node processes on **one machine over the loopback interface** (127.0.0.1). Discovery uses real multicast DNS packets, but on `lo0` and a private UDP port.
- The replicated store is the minimal last-writer-wins stand-in in `tests/helpers/lww-store.ts` (JSON messages, digest exchange on link-up, gossip). It is **not** the Phase 2 engine, so absolute throughput for real data will differ; the numbers characterise the transport (TLS + framing + deflate + flow control) under a representative message pattern.

## What these numbers do not tell you

- **Real Wi-Fi was not measured.** Loopback has no radio latency, no loss, no contention, ~tens of GB/s of bandwidth. Real 802.11ac/ax links add ~2-10 ms RTT (more with power save), 100-600 Mbit/s of shared throughput, and variable loss. Treat all latencies below as the transport's own floor (CPU + TLS + serialisation), and throughput as an upper bound limited by CPU rather than by the network.
- Multicast behaviour on real routers (IGMP snooping, client isolation, guest networks) is untested.
- Battery / radio wake cost on laptops and phones is untested.

## Method

- **Handshake**: in-process, 30 fresh device pairs. "Pairing" = `pairWith` call to both sides holding the signed record (QR flow, includes one TLS 1.3 handshake, two ECDSA/Ed25519 signatures per side and file persistence). "Sync connect" = `connectSync` (TCP connect + mutual TLS 1.3 handshake + fingerprint pin check + app hello exchange), 5 per pair (150 samples). "Identity creation" = Ed25519 + P-256 keygen + self-signed certificate + write to disk, 20 samples.
- **Single-change latency**: devices A and B (separate processes) paired and connected; A calls `put`, B records the arrival time in `onApplied`. Both timestamps are `process.hrtime.bigint()` (system-wide monotonic clock, so comparable across processes). 200 samples, 2 ms apart. 3-peer variant: 100 samples, A writes, B and C (full mesh) read.
- **Initial sync**: device A is seeded with N documents before any pairing; one or two empty peers then pair with A (which triggers dial and digest exchange). Time reported is from the peer's link-up to A until its last document was applied, measured inside the peer process. Docs are JSON `{title, notes (filler), n, tags, done}`; the size column is the filler size. In the 2-peer case the two peers are also paired with each other, so they gossip received documents to one another (visible as extra "docs received").
- **CPU / memory**: `process.cpuUsage()` deltas (user+system) and RSS read from each process around the sync; idle = 5 s with three connected, quiescent peers (keep-alive pings every 15 s).

### Notes on the numbers

- Repeated-character filler compresses ~50x, which makes those rows measure JSON parse/stringify and TLS more than the link; the **random** rows are the realistic worst case (incompressible content, wire bytes about equal to logical bytes). Real task data (titles, notes, ids) sits between the two.
- On incompressible data the sender still tries deflate on every message and discards the result when it does not shrink; that is part of the higher CPU in the random rows. A heuristic to skip compression for already-dense content is a possible later optimisation, not done here.
- With two peers pulling from A at once and also paired with each other, each receives roughly 2x the documents ("Docs received per peer" above 10000): the stand-in engine gossips accepted documents to all other links, so a document can arrive from both A and the other peer. The transport delivers each message once; avoiding the duplicate work is the Phase 2 engine's job (for example by gossiping only after the digest round settles, or sending digests that include what is in flight).
- Single-change latency is sub-millisecond on loopback, so on real Wi-Fi it will be dominated by the radio round trip, not by this code.
